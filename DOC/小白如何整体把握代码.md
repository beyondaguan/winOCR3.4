# 小白如何整体把握代码

> 面向刚接触 WinOCR 代码库的开发者，用一条主线串起「文件怎么连、改了怎么验、测试怎么跑」。

---

## 一、先看全貌：四层蛋糕

代码分四层，依赖方向**只能从上往下**，不可逆转：

```
main.py              ← 入口层：解析命令，组装 App + UI
  ↓
winocr/core/         ← 核心层：App 组合根、配置、管线、事件总线、插件注册表
  ↓
winocr/services/     ← 服务层：6 个插件轴（OCR/翻译/AI/捕获/附件/持久化）
  ↓
winocr/ui/tk/        ← UI 层：Tk 窗口、贴条、对话框（纯表现，不写业务）
```

**一句话记住**：core 不知道有哪些具体引擎，services 不知道界面长什么样，ui 不知道引擎内部怎么工作。三层之间靠**事件总线**和**Pipeline 接口**通信。

## 二、关键文件各自干什么

### 入口层

| 文件 | 职责 |
|------|------|
| `main.py` | 6 个子命令入口：`gui`/`console`/`doctor`/`models`/`config`/`ocr`。只做「解析参数 → 组装 App → 挂 UI」，不写业务逻辑 |

### 核心层（`winocr/core/`）

| 文件 | 职责 | 类比 |
|------|------|------|
| `app.py` | **组合根**：全应用唯一的接线处。发现插件 → 实例化 → 注入 services → 组装 Pipeline | 相当于「工厂总装线」 |
| `config.py` | 配置模型：7 个功能块（ocr/translate/ai/hotkey/ui/tts/plugin），从 `config.toml` 加载 | 相当于「设置面板的数据层」 |
| `pipeline.py` | 管线编排：持有各轴服务实例，提供 `ocr()`/`translate()`/`chat()`/`record()` 等高层动作 | 相当于「调度中心」 |
| `event_bus.py` | 线程安全事件总线：后台线程 `publish`，UI 线程 `subscribe`，17 个预定义事件 | 相当于「广播站」 |
| `registry.py` | 通用插件注册表：扫描包目录，自动发现基类的子类 | 相当于「招聘中心」 |
| `paths.py` | 路径真相来源：所有文件在哪都由它决定 | 相当于「门牌号系统」 |
| `capsule.py` | 场景胶囊：把截图/OCR/翻译/AI 分析打包成可由热键触发的原子能力 | 相当于「快捷动作」 |

### 服务层（`winocr/services/`）

6 个插件轴，每个轴统一模式：**基类(ABC) + 多个实现 + 注册表自动发现**。

| 轴 | 目录 | 基类 | 实现举例 |
|----|------|------|---------|
| OCR | `ocr/` | `OcrEngine` | RapidOcrEngine(本地)、VisionOcrEngine(云端) |
| 翻译 | `translate/` | `TranslateEngine` | Argos(离线)、GLM、Hunyuan、MyMemory(免Key) |
| AI | `ai/` | `AiProvider` | GlmChatProvider、OpenAiCompatProvider |
| 捕获 | `capture/` | `CaptureSource` | Screenshot(框选)、Clipboard(剪贴板)、File(文件) |
| 附件 | `attach/` | `AttachParser` | Image、PDF、Word、Excel、PlainText |
| 持久化 | `persistence/` | `Persistence` | JsonHistory(翻译历史)、KnowledgeBase(知识库) |

另外 3 个独立服务（非插件轴）：`hotkey.py`(热键)、`tts.py`(朗读)、`openai_compatible/`(共享客户端)。

### UI 层（`winocr/ui/tk/`）

| 文件 | 职责 |
|------|------|
| `app.py` | **TkUi**：UI 适配器。把用户操作翻译成 Pipeline 调用（丢后台线程），把事件总线结果经 `post()` 队列泵回主线程 |
| `main_window.py` | **MainWindow**：纯表现层。摆部件 + 显示结果，一行业务逻辑都不写 |
| `sticker.py` | **StickerWindow**：划词翻译小贴条。无边框置顶悬浮窗，含方向切换按钮 |
| `dialogs.py` | 7 个设置对话框：API设置/热键/历史记录/知识库/插件/关于/首次运行 |
| `chat_panel.py` | AI 对话面板：气泡界面 + 附件拖放 |
| `tray.py` | 系统托盘（可选依赖 pystray） |
| `guards.py` | `@ui_thread` 装饰器：非主线程调用 UI 方法时拦截 |
| `theme.py` | 多主题注册表 |

## 三、文件之间怎么耦合的

### 3.1 新增功能时涉及的典型耦合链

以本次「小贴图方向按钮」为例，改动涉及 3 个文件的闭环：

```
sticker.py（UI 层）
  │  用户点「译中」按钮
  ↓ 调用
sticker.py::_retranslate(target)
  │  把译文区置为「翻译中...」占位
  ↓ 调用
app.py::translate_sticker(text, target)          ← UI 适配器公开入口
  │  先弹占位贴条，再启动翻译
  ↓ 调用
app.py::_translate_to_sticker(text, target, explicit=True)
  │  busy 守卫 + 30s 看门狗
  ↓ 调用
pipeline.run_async(pipeline.translate, text, target, explicit, ...)
  │  丢到后台线程
  ↓
pipeline.py::translate(text, target, explicit)
  │  调用 TranslateDispatcher.translate_detailed()
  ↓
dispatcher.py::translate_detailed(text, target, explicit)
  │  detect() 推断源语言 → 按 fallback_order 逐个引擎尝试
  ↓ 返回 TranslateResult
  │
  ↓ on_done 回调（仍在后台线程）
app.py::_done(result)
  │  释放 busy → pipeline.record(写历史) → post(show_sticker, 原文, 译文)
  ↓ post() 投递到 UI 队列
  │
  ↓ 主线程 _pump_ui 取出执行
main_window.py::show_sticker(original, translation)
  │  转发给 StickerWindow
  ↓
sticker.py::show(original, translation)          ← 贴条更新显示
```

**耦合规则**：
- UI 层只调 `app.py`（TkUi）的方法，不直接碰 Pipeline
- TkUi 只通过 `pipeline.run_async()` 丢后台线程，不阻塞主线程
- 后台线程只通过 `post()` 投递回主线程，不直接碰 Tk 控件
- `@ui_thread` 守卫兜底：万一后台线程误碰 Tk 控件，会被拦截

### 3.2 新增对话框时的耦合

以本次「历史记录面板」为例，3 个文件闭环：

```
dialogs.py::open_history(window)           ← 实现历史面板 UI
  ↑ import
main_window.py L18                         ← 导入函数
  ↑ 接线
main_window.py L72                         ← 按钮 command=open_history
  ↑ 获取数据
dialogs.py → app.services["persistence"]   ← 读 JsonHistory 落盘的 history.json
```

## 四、改了代码怎么知道有没有同步

### 4.1 交叉验证法（grep 搜索）

改了某个函数名或新增了某个接口，用 grep 确认所有调用点都已更新：

```bash
# 例：新增了 translate_sticker 方法，确认所有调用点都能找到
grep -rn "translate_sticker" winocr/ tests/

# 例：新增了 open_history 函数，确认 import 和接线都在
grep -rn "open_history" winocr/ tests/
```

**判断标准**：
- 每个定义点（`def xxx`）都有对应的调用点
- 每个调用点引用的函数/方法都真实存在
- 测试文件中覆盖了新功能的关键路径

### 4.2 函数签名一致性检查

本次修复的一个真实案例：`_translate_to_sticker` 新增了 `explicit` 参数，但测试里的 mock `boom` 签名没同步：

```python
# 改动前（app.py 调用）
pipeline.run_async(pipeline.translate, text, target, explicit, ...)

# 测试 mock（没同步，炸了）
def boom(text, target, **kwargs):   # ← 缺 explicit 位置参数
    ...
```

**教训**：改了函数签名，一定要 grep 所有调用点和测试 mock。

### 4.3 前向引用检查

本次修复的另一个真实案例：`open_history` 中按钮 `command=_load` 直接引用了在后面才定义的函数，Python 会把它当未赋值的局部变量：

```python
# 有 bug（_load 在 L1407 定义，但 L1350 就引用了）
ttk.Button(top, text="搜索", command=_load)

# 修复后（用 lambda 延迟查找）
ttk.Button(top, text="搜索", command=lambda: _load())
```

**规则**：`command=` 直接传函数引用时，该函数必须在按钮创建之前已定义。用 `lambda` 包装可以延迟到点击时才查找。

```bash

.venv/Scripts/python.exe -m pytest tests/ -v
```

## 七、为什么 doctor 不需要更新

`doctor` 子命令（`main.py` L190）的工作是：

1. 打印路径信息（Python 版本/用户目录/配置/历史/插件目录）
2. 遍历 6 个轴的 discovered 插件，调 `inst.available()` 输出 `[+]`/`[-]`/`.`
3. 检查关键依赖（PIL/rapidocr/onnxruntime 等）能否 `__import__`
4. 检查 OCR 模型资源是否存在
5. 列出场景胶囊

本次新增的两个功能（方向按钮 + 历史面板）：
- 不新增插件轴、不新增服务、不新增依赖
- 纯 UI 层改动（`sticker.py`/`app.py`/`dialogs.py`/`main_window.py`）
- doctor 不扫描 UI 层文件，所以不需要更新

**什么时候 doctor 需要更新**：
- 新增了一个服务轴（如新增 `services/export/`）
- 新增了一个关键依赖（如新增 `import openpyxl`）
- 新增了模型资源路径
- 改变了插件发现机制

## 八、config.toml 黑名单的影响

用户的 `~/.winocr/config.toml` 中有：

```toml
[plugin]
blacklist = ["vision_ocr", "hunyuan", "json_history"]
```

**生效路径**：

```
AppConfig.load() → PluginConfig(blacklist=[...])
  ↓
App._discover(axis, base)                     (app.py L126)
  found = registry.discover(base, package)     → 发现所有插件
  found = {name: cls for name not in blacklist} → 过滤掉黑名单
```

**影响**：
- `json_history` 被黑名单 → `app.services["persistence"]` 为 None → `open_history` 会提示「历史记录服务未初始化」
- `vision_ocr` 被黑名单 → doctor 不显示云端 OCR
- `hunyuan` 被黑名单 → 翻译回退链跳过混元

**测试中的处理**：`test_gui_smoke.py::test_dialogs_build` 注入了 `_FakeStore` 来模拟 persistence 服务，不依赖用户配置。
