# 踩坑记录

> 专门记录 AI 编程过程中踩过的坑，供下次总结经验、避免重蹈覆辙。
> 每条记录包含：症状 → 根因 → 涉及文件链 → 修复方式 → 预防规则。

| P-02 | 前向引用 | 按钮引用了后面才定义的函数 | 测试弹窗失败 |

| P-11 | run.bat 退出只退「真实解释器」，留下 venv shim 父进程 | `.venv\pythonw.exe` 是重定向器，os._exit(0) 只退子进程 → 每次启动 run.bat 都要 stop_winocr 杀进程 | run.bat 每次报「检测到旧实例，执行强杀」 |

| P-13 | 退出强杀误伤 pytest：测试进程也由 venv shim 拉起 | `_force_exit_venv_tree()` 只看「父进程是 .venv shim」就 `taskkill /T` 杀父树，pytest 同样由 shim→真身拉起，被自己发出的 taskkill 连根杀死（无 traceback 的 exit=1） | 全量测试跑到一半进程被无 traceback 终止 |

## 二、踩坑详解

### P-01：Mock 签名不同步

**症状**：`test_translate_failure_still_releases_busy` 报 `AssertionError: 划词翻译进行中应置位 _busy`。

**根因**：

功能代码 `app.py` 的 `_translate_to_sticker` 给 `pipeline.run_async` 调用新增了第三个位置参数 `explicit`：

```python
# app.py L706-708（改动后）
self.app.pipeline.run_async(
    self.app.pipeline.translate, text, target, explicit,   # ← 新增 explicit
    on_done=_done, on_error=_err, cancel_event=self._cancel_event)
```

`pipeline.translate` 的签名是 `(text, target, explicit=False, note="")`，所以 `run_async` 把 `text, target, explicit` 三个位置参数传给了 `translate`。

但测试里的 mock `boom` 只收 2 个位置参数：

```python
# test_selection_translate_busy.py L51（改动前）
def boom(text, target, **kwargs):   # ← 第 3 个位置参数 explicit 没有着落
    time.sleep(0.3)
    raise RuntimeError("simulated network failure")
```

调用时 `boom('hello', 'en', False)` → `TypeError: boom() takes 2 positional arguments but 3 were given`。

这个 TypeError 在 `time.sleep(0.3)` 之前就抛出了，导致后台线程瞬间结束、`_busy` 瞬间释放。测试在 0.1s 后检查 `_busy.is_set()` 时已经是 `False`，断言失败。

**涉及文件链**：

```
winocr/core/pipeline.py L47-48         translate(text, target, explicit, note)  ← 签名源头
  ↓ 被调用
winocr/ui/tk/app.py L706-708           run_async(translate, text, target, explicit, ...)  ← 传参点
  ↓ 被测试 mock 替换
tests/test_selection_translate_busy.py L51    def boom(text, target, **kwargs)  ← mock 没同步
```

**修复**：

```python
# 修复后
def boom(text, target, explicit=False, note="", **kwargs):  # noqa: ANN001
```

**预防规则**：

> 改了任何被 `monkeypatch.setattr` 替换的方法签名，必须 grep 测试目录中的所有 mock 函数，逐个比对参数列表。`pipeline.translate` 的签名改了，所有替换它的 mock（`boom`/`fake_translate`/...）都要同步改。

### P-02：前向引用——按钮引用了后面才定义的函数

**症状**：`test_dialogs_build` 跑 `open_history(ui.window)` 时直接抛 `NameError` 或弹 `messagebox` 卡死。

**根因**：

`dialogs.py` 的 `open_history` 函数内部，按钮在 L1350 创建时直接传了函数引用 `command=_load`，但 `_load` 要到 L1407 才定义。Python 在函数体内部，把 `_load` 当作局部变量——在赋值之前引用就会 `NameError`。

```python
# dialogs.py（有 bug）
def open_history(window):
    ...
    ttk.Button(top, text="搜索", command=_load).pack(...)   # L1350: _load 还没定义
    ttk.Button(bar, text="复制原文", command=_copy_orig)     # L1384: _copy_orig 还没定义
    ttk.Button(bar, text="复制译文", command=_copy_tran)     # L1385
    ttk.Button(bar, text="清空历史", command=_clear)         # L1386

    def _load(): ...        # L1407: 在这里才定义
    def _copy_orig(): ...   # L1462
    def _copy_tran(): ...   # L1465
    def _clear(): ...       # L1468
```

对比同文件中已经用 lambda 的写法（L1349、L1351 等就没有问题），说明这是编写时的疏忽。

**涉及文件链**：

```
winocr/ui/tk/dialogs.py L1350     command=_load           ← 有 bug
winocr/ui/tk/dialogs.py L1384     command=_copy_orig      ← 有 bug
winocr/ui/tk/dialogs.py L1385     command=_copy_tran      ← 有 bug
winocr/ui/tk/dialogs.py L1386     command=_clear          ← 有 bug
  ↑ 同函数内
winocr/ui/tk/dialogs.py L1407     def _load()             ← 定义在后
winocr/ui/tk/dialogs.py L1462     def _copy_orig()        ← 定义在后
winocr/ui/tk/dialogs.py L1465     def _copy_tran()        ← 定义在后
winocr/ui/tk/dialogs.py L1468     def _clear()            ← 定义在后
  ↑ 知识库对话框也有同样问题
winocr/ui/tk/dialogs.py L1180     command=_load           ← 有 bug（已一并修复）
```

**修复**：

全部改成 lambda 延迟查找：

```python
# 修复后
ttk.Button(top, text="搜索", command=lambda: _load()).pack(...)
ttk.Button(bar, text="复制原文", command=lambda: _copy_orig()).pack(...)
ttk.Button(bar, text="复制译文", command=lambda: _copy_tran()).pack(...)
ttk.Button(bar, text="清空历史", command=lambda: _clear()).pack(...)
```

`lambda` 在点击时才执行 `_load()`，此时函数已经定义完毕。

**预防规则**：

> Tk 的 `command=` 参数如果直接传函数引用（`command=_load`），该函数必须在按钮创建之前已定义。如果函数定义在后面，必须用 `command=lambda: _load()` 延迟查找。新增对话框时，一律用 lambda 包装 `command=`，不直接传引用。

### P-03：测试覆盖遗漏——新增功能没纳入冒烟

**症状**：人工审查发现 `open_history` 没被任何测试覆盖。

**根因**：

`test_gui_smoke.py::test_dialogs_build` 遍历对话框构建测试，但只列了 3 个：

```python
# 修复前（L128-130）
for opener in (dialogs.open_hotkey_settings,
               dialogs.open_api_settings,
               dialogs.open_about):
```

新增的 `open_history` 没被加进循环。如果只是「代码跑通了」但没被测试覆盖，将来改 `open_history` 内部逻辑时不会有回归保护。

**涉及文件链**：

```
winocr/ui/tk/dialogs.py L1322          def open_history(window)    ← 新增功能
  ↑ 缺少测试覆盖
tests/test_gui_smoke.py L128-130       for opener in (...):        ← 没包含 open_history
```

**修复**：

```python
# 修复后
for opener in (dialogs.open_hotkey_settings,
               dialogs.open_api_settings,
               dialogs.open_about,
               dialogs.open_history):     # ← 补上
```

**预防规则**：

> 在 `dialogs.py` 中新增任何 `open_xxx` 函数后，必须同步加到 `test_gui_smoke.py::test_dialogs_build` 的遍历列表中。通用规则：**新增公开函数 → grep 测试目录确认有无覆盖 → 没有就补**。

### P-04：黑名单环境依赖——用户配置导致测试卡死

**症状**：`open_history` 在测试中弹 `messagebox.showinfo("历史记录服务未初始化")` 并卡死（`grab_set` 阻塞）。

**根因**：

用户的 `~/.winocr/config.toml` 配置了插件黑名单：

```toml
[plugin]
blacklist = ["vision_ocr", "hunyuan", "json_history"]
```

`json_history` 被黑名单后，`App._discover()` 在过滤阶段把它删掉，`app.services["persistence"]` 为 None。`open_history` 开头检查到 `store is None` 就弹 messagebox，在 headless 测试环境中 `grab_set()` 阻塞。

**涉及文件链**：

```
~/.winocr/config.toml                      blacklist = ["json_history"]
  ↓
winocr/core/app.py L126-134                _discover() 过滤掉黑名单插件
  ↓
winocr/core/app.py L92-95                  persistence = None（pcls 为空）
  ↓
winocr/core/app.py L117                    services["persistence"] = None
  ↓
winocr/ui/tk/dialogs.py L1330-1333         if store is None: messagebox.showinfo(...)  ← 卡死
  ↓
tests/test_gui_smoke.py                    test_dialogs_build 弹窗阻塞
```

**修复**：

在测试中注入 mock store，不依赖用户配置：

```python
class _FakeStore:
    def load_records(self):
        return []
    def clear(self):
        pass
app.services["persistence"] = _FakeStore()
```

**预防规则**：

> 测试不能依赖用户的 `config.toml` 配置。凡是读取 `app.services` 的功能，测试中必须显式注入 mock，确保黑名单/缺依赖等环境差异不影响测试。**读 config.toml 的功能 = 测试中必须 mock 对应 service**。

### P-05：功能代码与测试代码的同步盲区

**症状**：功能代码改了 4 个文件，但测试代码没同步更新，导致 1 个测试失败 + 1 个测试缺失覆盖。

**根因**：

AI 改功能代码时，注意力集中在「让功能跑起来」，没有自动执行「改了什么 → 哪些测试要跟着改」的检查。典型表现：

| 功能改动 | 测试应该同步 | 实际有没有同步 |
|---------|------------|-------------|
| `app.py` 给 `run_async` 传参加了 `explicit` | `boom` mock 签名加参数 | ❌ 没同步（P-01） |
| `dialogs.py` 新增 `open_history` | `test_dialogs_build` 加进遍历列表 | ❌ 没同步（P-03） |
| `dialogs.py` 新增 `open_history` 依赖 persistence | 测试注入 mock store | ❌ 没同步（P-04） |
| `dialogs.py` 的 `command=` 前向引用 | 无直接测试，但冒烟构建能暴露 | ❌ 没跑冒烟就交付 |

**预防规则**：

> 每次改完功能代码，必须执行以下同步检查清单（详见第四节）。

### P-06：Tk Label 内嵌子部件压字（3.4.18 项目标签）

**症状**：项目标签栏里非默认项目的文字只露出一个字符，其余被裁；「✕ 关闭」可见但文字被挤没。

**根因**：把「✕」作为子部件 `pack(side=RIGHT)` 嵌进 `tk.Label`。Label 的几何算法对子部件处理不可靠，子部件反而抢占文字渲染区（文字宽度没有扣减子部件占位）。

**涉及文件链**：`winocr/ui/tk/project_bar.py::ProjectTabBar.refresh`

**修复方式**：放弃「Label 嵌子部件」，改用 **Frame 做容器**：

```python
tab = tk.Frame(self.frame, bg=bg, highlightthickness=1)   # 容器（边框/背景）
inner = tk.Frame(tab, bg=bg); inner.pack(padx=12, pady=4)  # 统一内边距
name_lbl.pack(side=tk.LEFT)                                 # 文字
x_lbl.pack(side=tk.LEFT)                                    # ✕ 并排，不再重叠
```

**预防规则**：

> 需要「文字 + 可点小部件」组合时，一律用 Frame 并排容器，不要往 Label 里 pack 子部件。

### P-07：热键录制写错属性（3.4.18 热键录制）

**症状**：设置里新录 `ALT+Q` 截图热键，立即无效；重启也不保留；旧的 `Ctrl+Shift+A` 一直生效。

**根因**：录制回调把组合键写进了 `setattr(cfg, action, combo)` 的**临时属性**，而 `HotkeyService.resolved()` 只读 `cfg.overrides.get(action)` → 永远回退胶囊默认；且临时属性不参与 `save()` 序列化 → 不落盘。

**涉及文件链**：`winocr/ui/tk/dialogs.py::open_hotkey_settings`、`winocr/services/hotkey.py::resolved`、`winocr/core/config.py::HotkeyConfig`

**修复方式**：录制统一写 `cfg.overrides[action] = combo`（清空则 `pop` 恢复胶囊默认），保存走 `apply_config()`（落盘）+ `hotkeys.reload()`（重注册）。配套 `tests/test_hotkey_override.py` 钉死「任意新键覆盖旧键 + 立即生效 + 重启保留」。

**预防规则**：

> 配置类「用户可录制的覆盖值」一律进显式 `overrides` 字典并走 `apply_config()` 持久化；不要用 `setattr` 往 dataclass 上挂临时字段（`save()` 序列化不到）。

### P-08：老知识库 schema 不兼容（3.4.18 用户真实库踩坑）

**症状**：用户从 `WinOCR-Portable-v1.0.0` 升级后，点「存知识库」报 `保存失败: table knowledge has no column named scene`，所有写入失败。

**根因**：旧版 schema 字段名是 `scenario`（不是 `scene`），并多了 `tags` / `note` 列。`CREATE TABLE IF NOT EXISTS` 不会重建已存在表，新代码 INSERT `scene` 列就报无该列。

**涉及文件链**：`winocr/services/persistence/knowledge.py::_init_db` / `save_knowledge` / `_row_to_record` / `import_records` / `export`

**修复方式**：在 `_init_db` 里加幂等迁移 `_migrate_legacy_columns`：
1. 缺 `scene` 但有 `scenario` 时：`ALTER ADD scene` + `UPDATE scene = scenario`（仅填空行，不覆盖已有）；
2. `tags` / `note` 缺则 `ALTER ADD DEFAULT ''`（保留老数据）；
3. `KnowledgeRecord` 加兼容字段 `scenario` / `tags` / `note`；`_row_to_record` 用「先试取」安全读；`export` 把 `scenario` 合并到 `scene` 输出；`import_records` 探测 schema 动态构造 INSERT 列，并接收 dict 的 `scenario` 字段。

**预防规则**：

> 加新字段或改字段名时，永远不要相信 `CREATE TABLE IF NOT EXISTS` 会重建老库。`_init_db` 必须**探测列并幂等迁移**，且读写函数都按列「先试取」兼容老 schema。导出格式里同时写新旧字段名（如 `scene` + `scenario`），导入按探测到的列动态 INSERT。

### P-09：第三方库线程引用丢失（pystray）

**症状**：点托盘菜单「退出 WinOCR」后，图标仍留在系统托盘、进程不退出，必须用 `stop_winocr.py` 强杀。

**根因**：

pystray Win32 后端的 `_run_detached()` 源码：

```python
def _run_detached(self):
    threading.Thread(target=lambda: self._run()).start()
```

线程创建后直接 `start()`，**不存储引用**。导致：
1. `TrayIcon.stop()` 无法 `thread.join()` 等线程退出（`self._thread` 为 None）；
2. 无法将线程设为 `daemon=True`（非 daemon 线程会拖住进程退出）；
3. `icon.stop()` 只发停止信号但不等线程真正退出 → Tk 主线程销毁后，该非 daemon 线程仍在跑消息循环 → 进程不退。

**涉及文件链**：`ui/tk/tray.py`（start/stop）→ `ui/tk/app.py`（quit_app 调 tray.stop）

**修复方式**：

1. **patch `_run_detached`**：在 `TrayIcon.start()` 中用实例级函数替换 `pystray.Icon._run_detached`，自建 `daemon=True` 线程并保存引用到 `self._thread`：
   ```python
   def _patched_run_detached():
       t = threading.Thread(target=lambda: icon_ref._run(), daemon=True)
       self._thread = t
       t.start()
   self._icon._run_detached = _patched_run_detached
   self._icon.run_detached()
   ```
2. **`quit_app` 末尾 `os._exit(0)` 兜底**：即使 join 超时也保证进程退出。
3. **`Ctrl+Shift+Q` 全局闸门**：热键服务中 `enabled=False` 时也始终注册，是程序最后逃生口。

**预防规则**：

> 用第三方库启动后台线程时，不要假设库会存储线程引用或设 daemon。必须自己 patch 或包装来捕获线程引用 + 设 daemon + 提供 join 接口。进程退出路径末尾一律加 `os._exit(0)` 兜底，防止任何遗漏的非 daemon 线程拖住进程。

### P-10：虚拟环境「AI 跑的解释器 ≠ run.bat 跑的解释器」（3.4.17 进程残留排查）

**症状**：反复修改知识库面板代码、验证导入正常，但用户截图里面板仍是旧版；用 `stop_winocr.py --force` 强杀后总能查出「2 个残留进程」。

**根因**：

同一份 `D:\winOCR3.4` 源码，存在**两组可运行它的解释器进程**：

- `run.bat` 用 `.venv\Scripts\pythonw.exe main.py` 启动；
- `.venv\Scripts\pythonw.exe` 在 Python 3.12 下是个 **launcher/stub**，它又会拉起 `D:\Documents\Programs\Python312\pythonw.exe` 作为**真正跑代码的子进程**。

实际进程列表（用 `tools/list_winocr_proc.py` 看到）:

```
PID=26248 (Parent=12760)  .venv\Scripts\pythonw.exe main.py      ← shim 父进程
PID=2344  (Parent=26248)  D:\Documents\Programs\Python312\pythonw.exe main.py  ← 真身子进程
```

两个进程都加载 `D:\winOCR3.4\winocr` 的源码（`sys.path[0]` 是脚本所在目录），但：
1. **PID / PYID 不同**、解释器可执行文件路径不同、进程树父子关系不同；
2. AI / 工具脚本若用带控制台的 `D:\Documents\Programs\Python312\python.exe` 跑（比如跑 pytest），**它和用户双击 run.bat 起的 GUI 进程不是同一个解释器进程**——虽然加载同一份源码，但互相独立，杀一个另一个还在；
3. `stop_winocr.py --force` 按「命令行含 main.py」匹配，每次都能抓到父子两个 PID，看起来就像「残留 2 个」。

这就是「AI 验证代码没问题，但用户看到旧行为」的常见误判源：**AI 跑的是自己的解释器进程，用户跑的是另一个**，两者在不同时间启动，加载的是同一份源码，所以如果源码确实改了，用户那边重启后应生效——但因进程没杀干净 / AI 与用户环境不一致，排查被误导。

**涉及文件链**：

```
run.bat                                        .venv\Scripts\pythonw.exe main.py  ← 用户入口（shim）
  ↓ shim 转发
D:\Documents\Programs\Python312\pythonw.exe  main.py  ← 真身子进程
  ↓ 加载
D:\winOCR3.4\winocr\...                       同一份源码
  ↑ 另一套进程
D:\Documents\Programs\Python312\python.exe   main.py / pytest  ← AI / 工具的进程
```

**修复方式**：

1. **新增进程查看工具** `tools/list_winocr_proc.py`：
   - 列出所有 python 进程的 PID、ParentPID、Name、可执行文件路径、命令行；
   - 画 WinOCR 相关进程的**父子树**；
   - 支持 `--all`（含 IDE/pytest 等无关 python 进程）、`--pid <xxx>`（单查）。
   排查任何「改了没生效 / 进程没退干净」问题前，先跑它看清当前到底哪几个进程在跑、谁是谁的父进程。
2. **退出逻辑面向「进程树」**：杀进程用 `taskkill /F /T /PID`（`/T` 连子进程一起杀，`kill_winocr.py` 已用），程序内部退出用 `quit_app` 末尾 `os._exit(0)` + 兜底线程（见 P-09）。

**预防规则**：

> 排查「改代码没生效 / 进程残留」时，第一件事是用 `tools/list_winocr_proc.py` 列出所有 python 进程及其父子树，分清「AI 跑的解释器进程」和「用户 run.bat 跑的解释器进程」——它们 PID/PYID 不同、可执行文件可能不同、但加载同一份源码。不要只凭「导入正常 / 语法通过」就判定改动生效，要看**用户那个进程**有没有重启并在跑新代码。虚拟环境 shim（`.venv\pythonw.exe`）会拉起系统 Python 子进程，杀进程要按进程树（`/T`）杀，否则父进程残留。

### P-11：run.bat 退出只退「真实解释器」，venv shim 父进程残留 → 每次启动都要杀进程（3.4.17）

**症状**：双击 run.bat 每次启动都打印「检测到旧实例（PID: xxxx xxxx），先关闭再启动…，执行强杀」。明明上次托盘右键退出了，进程却没退干净。

**根因**：

`run.bat` 用 `.venv\Scripts\pythonw.exe main.py` 启动，而这个 pythonw.exe 是**重定向器（shim）**，它会再拉起真正解释器 `D:\Documents\Programs\Python312\pythonw.exe` 作为**子进程**来跑代码：

```
run.bat
  ↓ start "" .venv\Scripts\pythonw.exe main.py
shim 进程    .venv\Scripts\pythonw.exe main.py      ← 父（重定向器，等待子进程）
  ↓ 拉起子进程
真身子进程   D:\Documents\Programs\Python312\pythonw.exe main.py
```

代码（含 `quit_app` 末尾的 `os._exit(0)`）跑在**真身子进程**里。`os._exit(0)` 只结束**当前**进程 = 真身子进程，**不会关掉父 shim**。于是每次退出后 shim 父进程残留，下次 run.bat 就要 stop_winocr.py 强杀。

用 `_exit_diag.py` 实测确认：启动后是 `shim(16320) → 真身(17612)` 两个进程，托盘退出后两个都不消失（因为根本没走到退出，或只退了子进程）。

**涉及文件链**：

```
run.bat                                        start "" .venv\Scripts\pythonw.exe main.py
  ↓
winocr/ui/tk/app.py  _force_exit_venv_tree()   新增：检测父进程是 .venv shim → taskkill /T 连父带子一起杀
  ↓ 调用点
winocr/ui/tk/app.py  quit_app()                之前的兜底 = os._exit(0) 只退自己（根因）
winocr/ui/tk/app.py  _tray_quit()              2 秒强退线程也改为调 _force_exit_venv_tree()
```

**修复方式**：

新增 `_force_exit_venv_tree()`：退出时用 Windows Toolhelp API 查当前进程的父进程，若父进程是 `.venv` 下的 python/pythonw（即 venv shim），就对父进程树执行 `taskkill /F /T /PID <父PID>`——`/T` 把父 shim 和它所有子进程（含自己）一起强杀，绝不残留；否则（测试 / 命令行 / IDE 直接跑）只 `os._exit(0)`，**绝不误杀父进程**。

关键点：判断是不是 shim 用「父进程可执行文件路径含 `\.venv\` 且以 python/pythonw.exe 结尾」，且父进程 ≠ 自己。这样能精准对上 run.bat 场景，又不会把终端 / IDE / 测试进程当父进程强杀。

> 二次踩坑：第一版还加了「父进程命令行含 main.py」的守卫，结果在 pythonw 环境里用 PowerShell 查父进程命令行（`Get-CimInstance ... CommandLine`）**返回空字符串**，守卫静默失败 → taskkill 分支永不触发，进程照样残留（真机复现时每启动一次都报「检测到旧实例强杀」）。教训：**pythonw 下别靠 PowerShell 查父进程命令行做判定**，用 Toolhelp 快照读父进程可执行文件路径这种硬特征才可靠。
>
> 三次踩坑（见 P-13）：只凭「父进程是 .venv shim」就 taskkill 会误杀 pytest——pytest 同样由 shim→真身拉起。最终判定改为「父进程是 .venv shim **且** 当前进程命令行含 main.py」（`GetCommandLineW` 读当前进程，不依赖 PowerShell），只有 run.bat 起的 GUI 才满足。

**预防规则**：

> 只要是通过 venv shim（`.venv\Scripts\python(w).exe`）启动的 GUI，退出就别只用 `os._exit(0)`——它只退**真身子进程**，shim 父进程会残留。要么在本进程里查父 shim 并 `taskkill /F /T`，要么统一用 `stop_winocr.py`（已带 `/T`）兜底。判定「进程干净退出」看 `tools/list_winocr_proc.py` 是否一条相关进程都不剩。

**验证结论（2026-08-24 真机）**：托盘右键退出后，`python tools\list_winocr_proc.py` 中不再有任何 `main.py` 进程（shim 与真身一起消失）；再次双击 run.bat 不再打印「检测到旧实例，执行强杀」，直接启动。`run.bat` 里的 `stop_winocr.py --quick` 保留为「单实例守卫 + 异常兜底」，无旧实例时秒退、不拖慢启动，无需删除。

### P-12：PID 动态不可当身份 —— 用「固定解释器 ID = PYID」做人机对账（3.4.17）

**症状 / 用户需求**：AI 与用户各自跑代码，A 说「我改了，重启生效」，用户看到还是旧行为。想用一个「ID」对账，但 OS 进程的 PID 一次一个样（动态），不知道拿什么固定。

**根因**：

- **PID 是 OS 每次运行分配的动态值**，同一段代码每次启动 PID 都不同，不能当身份；
- 能当固定身份的，是「解释器可执行文件」本身：同一台机器、同一份虚拟环境，它 `resolved` 后的绝对路径每次都一样；
- 所以固定 ID 应从**解释器路径**导出，而不是 PID。

**「固定 ID 跑」的方案（PYID）**：

```
步骤 1：把进程的可执行文件解析（resolve）到「真实解释器」路径
        .venv\Scripts\pythonw.exe ──读 pyvenv.cfg 的 home──► D:\Documents\Programs\Python312\pythonw.exe
步骤 2：对该真实路径做 sha1，取前 10 位 → 得到一个短 ID，叫 PYID
        sha1("d:\documents\programs\python312\pythonw.exe")[:10] = 0162f86e4f
步骤 3：PYID 只依赖解释器路径，不依赖 PID → 每次运行都相同（固定）
```

判断「AI 跑的和我 run.bat 跑的是不是同一个解释器」= **比对 PYID 是否相同**，与 PID 多少无关。

**涉及文件链**：

```
tools/list_winocr_proc.py        新增 PYID 列 + --pyid 反查 + 按 PYID 归并
  └─ _resolve_real()              读 pyvenv.cfg 的 home 把 shim resolve 到真实解释器（确定性，不靠进程树）
  └─ _pyid()                      sha1(真实解释器路径)[:10]
```

**修复方式**：

`tools/list_winocr_proc.py` 升级：

```
python tools/list_winocr_proc.py                 看 WinOCR 进程 + PYID + 归并
python tools/list_winocr_proc.py --pyid 0162f86e4f   反查同一解释器下的所有进程
```

注意：resolve 必须**读 `pyvenv.cfg` 的 home**，不要靠「沿父→子进程找」——因为 `.venv\Scripts\python.exe`（如 pytest）有时不产生可见子进程，走进程树会算出不同的 PYID，反而误导对账。

**预防规则**：

> 人和 AI 讨论「跑的是哪个解释器」时，**用 PYID 不用 PID**——PID 每次运行都变。统一口径：让 `tools/list_winocr_proc.py` 输出 PYID，双方比对 PYID 是否一致。要使 PYID 固定，就把它绑定到「resolved 真实解释器路径」的哈希，而不是任何动态的进程号。

### P-13：退出强杀误伤 pytest —— 测试进程也由 venv shim 拉起（3.4.17）

**症状**：跑全量测试时，pytest 进程跑到一半**无任何 traceback 地被终止**（exit=1，输出只有几个点）。单独跑每个测试都通过，组合跑就崩。用 `-x` 定位到 `test_quit_app_cleans_up_and_force_exits` 之后进程消失。

**根因**：

`_force_exit_venv_tree()` 第一版只判断「父进程是 `.venv` 下的 python/pythonw（venv shim）」就执行 `taskkill /F /T /PID <父PID>`。但**pytest 进程同样由 venv shim 拉起**：

```
.venv\Scripts\python.exe -m pytest ...      ← shim 父进程（PID 15656）
  ↓ 拉起真身
D:\Documents\Programs\Python312\python.exe -m pytest ...   ← 测试进程（self）
```

测试进程的父进程恰好是 `.venv\Scripts\python.exe`（venv shim）→ 满足判定 → 测试进程**自己发出** `taskkill /F /T /PID 15656`。`/T` 连子进程一起杀，把 shim 父进程和**测试进程自己**一起杀掉了 → 无 traceback 的 exit=1。

用 `_win32_parent_info()` 实测确认：pytest 进程的父进程就是 `D:\winOCR3.4\.venv\Scripts\python.exe`。

**涉及文件链**：

```
winocr/ui/tk/app.py  _force_exit_venv_tree()   只看父进程是 venv shim → 误杀 pytest（根因）
winocr/ui/tk/app.py  _current_cmdline_has_main_py()  新增：GetCommandLineW 读当前进程命令行
```

**修复方式**：

判定收紧为「父进程是 .venv shim **且** 当前进程命令行含 main.py」：

```python
def _current_cmdline_has_main_py() -> bool:
    k32 = _ct.windll.kernel32
    k32.GetCommandLineW.restype = _ct.c_wchar_p
    cmd = k32.GetCommandLineW() or ""
    return "main.py" in cmd.lower()
```

- run.bat 起的 GUI：命令行 `.venv\Scripts\pythonw.exe main.py` → 含 main.py → 杀父 shim ✓
- pytest：命令行 `...python.exe -m pytest ...` → 不含 main.py → 只 `os._exit(0)`，不杀父进程 ✓
- 用 `GetCommandLineW` 读**当前进程**命令行，不依赖 PowerShell（pythonw 下 PowerShell 查命令行返回空，见 P-11 二次踩坑）。

**预防规则**：

> 任何「杀父进程树」的逻辑，**不能只看父进程特征**，必须同时确认当前进程身份（如命令行含 main.py）。因为「由 venv shim 拉起的进程」不止 run.bat 的 GUI——pytest、工具脚本、IDE 都可能由 shim 拉起。只凭父进程是 shim 就 `taskkill /T`，等于让进程自己杀自己所在的进程树。

## 五、AI 编程行为准则（从踩坑中提炼）

### 准则 1：改签名 = grep 全部 mock

> 改了任何被 `monkeypatch.setattr` 替换的方法签名（加参数、改参数名、改默认值），必须 `grep -rn "def.*mock\|def.*boom\|def.*fake" tests/` 逐个比对。

### 准则 2：新增公开函数 = 补冒烟覆盖

> 在 `dialogs.py` / `sticker.py` / `main_window.py` 中新增任何 `open_xxx` / `show_xxx` 公开函数，必须同步加到 `test_gui_smoke.py` 的遍历列表。

### 准则 3：command= 一律用 lambda

> Tk 的 `command=` 参数一律用 `command=lambda: func()` 包装，不直接传函数引用。避免前向引用 bug。

### 准则 4：测试不碰用户配置

> 测试中不读取用户的 `~/.winocr/config.toml`。凡依赖 `app.services` 的功能，测试中必须显式注入 mock。

### 准则 5：改完先跑相关测试再跑全量

> 不要改完直接跑全量 119 个测试。先跑与改动相关的 2-3 个测试文件，确认同步后再跑全量，节省排障时间。

### 准则 6：交付前 grep 确认调用链闭合

> 改了 A 调 B，要确认 B 存在；改了 B 的签名，要确认 A 的调用参数匹配。用 `grep -rn "函数名" winocr/ tests/` 做一遍全链检查。
