# 修复节奏（团队规范）

> 所有 bug 修复 / 回归修复 / 测试同步，一律按此 5 步推进，不跳步。

---

## 标准流程

```
定位根因（追到配置 / 初始化源头）
   ↓
先改 / 补冒烟测试（让其为红）
   ↓
改代码（最小修复 + 全局同类统一）
   ↓
冒烟 + 单测从红变绿
   ↓
更新 DOC/踩坑.md（沉淀根因链 + 耦合清单）
```

---

## 逐条展开

### 1. 定位根因（追到配置 / 初始化源头）

不停在「报错的那一行」。沿调用链往上追，直到找到真正的源头——配置值、初始化时序、插件发现阶段、签名变更点。

**检查清单**：
- 报错函数的上游调用方传了什么参数？
- 参数值从哪来——代码硬编码、config.toml、运行时推断？
- 是不是插件黑名单 / 缺依赖 / 环境差异导致 service 为 None？
- 是不是某次改签名后 mock 没同步？

**反面案例**：测试报 `_busy.is_set()` 断言失败，如果只看 L74 那行断言，永远找不到根因。往上追才发现 `boom` mock 签名缺 `explicit` 参数 → `TypeError` 在 `sleep` 之前抛出 → `_busy` 瞬间释放。

### 2. 先改 / 补冒烟测试（让其为红）

先写一个能复现 bug 的测试，确认它是红的（失败），再改代码。这样修完后从红变绿才算真正解决。

**检查清单**：
- 这个 bug 有没有现成的测试覆盖？没有就先补一个。
- 新增功能有没有被冒烟测试遍历？没有就加进去。
- 测试是否依赖用户 config.toml？是则注入 mock，不碰外部配置。

**反面案例**：`open_history` 前向引用 bug，如果 `test_dialogs_build` 的遍历列表里没有 `open_history`，这个 bug 永远不会被测试发现。

### 3. 改代码（最小修复 + 全局同类统一）

用最小改动修复根因，然后 grep 全局看有没有同类问题，一并修掉。

**检查清单**：
- 改动是否最小？不夹带无关重构。
- grep 同类模式：`grep -rn "command=_" winocr/`（前向引用）、`grep -rn "def boom" tests/`（mock 签名）。
- 改了函数签名 → grep 所有调用点 + 所有测试 mock。
- 新增 `command=` → 一律用 `lambda` 包装。

**反面案例**：修了 `open_history` 的 `command=_load` 前向引用，如果没 grep 全局，就不会发现 `open_knowledge` 里 L1180 有完全相同的 bug。

### 4. 冒烟 + 单测从红变绿

跑相关测试（不是直接跑全量 119 个），确认从红变绿。然后跑全量确认没有回归。

**命令**：
```bash
# 先跑相关的
.venv/Scripts/python.exe -m pytest tests/test_xxx.py -v --tb=short

# 再跑全量
.venv/Scripts/python.exe -m pytest tests/ -v --tb=short

# 最后 doctor
python main.py doctor
```

**检查清单**：
- 之前红的测试现在绿了？
- 全量没有新增失败？
- doctor exit 0？
- 没有临时 print / breakpoint 残留？

### 5. 更新 DOC/踩坑.md（沉淀根因链 + 耦合清单）

修复完成后，把根因链、涉及文件清单、预防规则沉淀到 `DOC/踩坑.md`，供下次参考。

**必须记录**：
- 症状（测试报了什么错）
- 根因链（从报错点追到源头，列出每一跳的文件 + 行号）
- 修复方式（改了什么，为什么这样改）
- 涉及文件清单（功能代码 + 测试代码 + 被波及但不需改的文件）
- 预防规则（一句话可执行的规则）

---

## 节奏约束

| 规则 | 说明 |
|------|------|
| 不跳步 | 不允许「改了代码 → 直接跑全量」，必须先让测试为红 |
| 不扩面 | 修复阶段不夹带重构、不改无关代码，最小改动优先 |
| 不留坑 | 同类问题必须 grep 全局统一修，不修一半 |
| 不沉默 | 修完必须更新踩坑文档，不修完就走 |
